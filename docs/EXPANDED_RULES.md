# 9/17 확장: 자판기의 옆문까지 확인하기

이 문서는 AI가 구현·실행한 내용이다. 사용자가 직접 설명하거나 실습한 것은 아직 확인하지 않았다.
비공개 정답을 알거나 모든 Solidity 프로그램을 증명하는 도구는 아니다.

## 1. 무엇이 달라졌나

예전 분석기는 자판기 설명서를 한 줄로 읽었다. 이제 작은 갈림길과 도우미 함수까지 따라간다.

```text
소스 → solc/Slither가 만든 코드 구조 → 성공할 수 있는 경로의 조건/변경/호출
     → 기존 네 규칙 + 확장 토큰/금고 규칙 → 파일별 판정 → 기존 CLI JSON
```

- **상한:** 쿠폰 최대 개수를 검사하는 옆으로 빠져나가는 길, 엉뚱한 수량 검사,
  마음대로 바꾸는 천장, 두 번째 발행 버튼, 한 번에만 제한하는 발행을 구분한다.
- **함수:** 다른 내부 함수에 맡긴 일과 인자를 연결한다. 단일 생성자 범위의 같은 파일 상속도 읽는다.
- **승인:** 남의 쿠폰은 허락 없이 옮길 수 없어야 한다. 사용한 허락을 차감하지 않고 계속 쓰는 경우도 찾는다.
- **정지:** 모두 정지하는 것과 관리자만 통과하는 것을 구분한다. 전송에 사용되지 않는 명단도 구분한다.
- **금고:** 자기 예치금 출금과 관리자의 예치금 전액 회수를 구분한다.
- **재진입:** 돈을 지급한 뒤 장부를 0으로 만드는 짧은 경로에서, 장부가 남은 틈의 중복 출금을 찾는다.
  지급 전 차감, 실제 잠금, 지급분의 checked 차감으로 초과 지급이 취소되는 제한된 정상 경계도 구분한다.
- **오탐 방지:** 상한 초과 때 `revert`, 외부 호출 없는 사후 검사, 실행 불가능한 분기,
  발행량 0, 사용되지 않는 private 함수, 잠금을 공유하지 않는 다른 출금 경로를 함께 검토한다.

`BENIGN`은 지원 범위 안의 모든 상태 변경 경로를 설명한 경우에만 낸다.
타인 자산 이동 등 충분한 위험 근거가 있으면 다른 미지원 컨트랙트가 있어도 `MALICIOUS`로 집계한다.
컴파일/파일 격리/시간 예산/stdout JSON 구조와 reference 원본·schema는 유지했다.

## 2. 코드에서 어디를 읽을까

| 파일 | 역할 | 쉬운 비유 |
| --- | --- | --- |
| `src/track1/rules/paths.py` | Slither 분기/내부 호출에서 조건·쓰기·호출 순서 수집 | 갈림길 지도 그리기 |
| `src/track1/rules/checked.py` | 무시하면 안 되는 checked 산술과 명백한 실패 확인 | 중간에 기계가 멈추는지 확인 |
| `src/track1/rules/expanded_tokens.py` | 발행 경계·승인·대칭 제한·관리 쓰기 검토 | 쿠폰 개수와 주인의 허락 검사 |
| `src/track1/rules/expanded_vaults.py` | 예치/출금/전체 회수/임의 실행/제한된 재진입 | 금고 장부와 송금 연결 |
| `src/track1/verdict.py` | 기존 규칙과 확장 규칙을 계약/파일 단위로 집계 | 검사 결과 모으기 |
| `tests/build_variants.py` | 별도 개발 문제와 기대 이유 생성 | 연습 문제 만들기 |
| `tests/test_expanded.py` | 정상·위험·이름 변경·미지원 경계 회귀 | 틀린 문제 다시 풀기 |
| `scripts/compare_baseline.py` | 기본 Slither 경고 실제 실행/기록 | 기존 도구와 역할 비교 |

Python에서 함수를 호출하면 인자를 전달하는 것처럼, 내부 Solidity 함수에 전달되는 값의
유래를 연결한다. 변수는 이름 문자열 대신 Slither 선언 객체로 구분한다.
`if`의 두 방향을 분리하고 `require`/`revert`와 변경 순서를 보존한다.
검사 실패가 앞선 상태 변경까지 취소한다는 점을 고려하되, 외부 호출은 금고 규칙에서 따로 다룬다.

## 3. 실제 수정 사이클

1. 기존 테스트 11개 통과(변경 전 63.336초). 처음 만든 29개 개발 문제는 정답 5/보류 24/오답 0.
2. 경로/토큰/금고 확장 후 29개 중 정답 28/보류 1/오답 0.
   `if (새공급량 > 상한) revert()`를 반대 방향의 `<=` 검사와 연결하지 못했다.
3. 비교식의 참/거짓 방향을 같은 형태로 정리해 수정. 상속·인자 modifier·잠금·모순 조건 등을
   포함한 40개 개발 문제는 정답 40/보류 0/오답 0으로 확인했다.
4. 기존 테스트 하나가 실패했다. 실제 동작 고장이 아니라 예전 `cap_bypass → UNCERTAIN` 기대값이었다.
   이제 실제 위험을 탐지하므로 `MALICIOUS`와 우회 이유를 검증하도록 변경했다.
5. 40개 전체를 이름/주석/공백/Unicode로 바꾼 사본에서도 판정과 실제 줄 위치를 확인했다.
6. 마지막 리뷰에서 자산이 없거나 초기 공급량이 자료형 최대인 경우, `_`에 도달하지 않는 modifier,
   무시된 산술 실패를 위험 실행으로 오인하지 않도록 보류 경계를 추가했다.

총 40개는 **정상 24개, 위험 16개**다. 이 숫자는 우리가 설계한 개발 문제의 결과다.
9/17 당시 `python -m unittest discover -s tests -v`: **17개 테스트, 63.937초, OK**. 현재 검증은 [제출 검증](experiments/submission-check.json)을 참고한다.
원본 JSON은 `docs/experiments/expanded-results.json`, 검증 코드/문제의 SHA256은 `docs/experiments/experiment-snapshot.json`에 보존했다.
공개 5개와 개발 변형, 이름 변경 사본은 서로 독립적인 비공개 평가셋이 아니다.
EVM 배포/공격 트랜잭션 실험을 수행한 것은 아니며, 실제 solc 컴파일과 CLI 정적 분석을 실행한 결과다.
기대 정답의 AI 검토를 사용자가 위임했으며 사용자 본인의 검토 완료로 기록하지 않았다.

## 4. 기본 Slither와 무엇이 다른가

Slither 0.11.6, solc 0.8.20의 기본 detector를 대표 10개 파일에 실제 실행했다.
기록은 `docs/experiments/slither-baseline.json`, 상세 원본은 `results/baseline/`에 있다.

| 사례 | 기본 Slither에서 관찰한 경고 | 자체 판정의 추가 연결 |
| --- | --- | --- |
| P2/P3, 상한 우회, 승인 없는 전송 | 이 실행에서는 constable/immutable/solc-version 종류 | 공급량·권한·전송 가능성·사용자 영향으로 대회 판정 |
| P5 | controlled-delegatecall 등 | 사용자 예치 경로와 임의 실행 권한을 연결 |
| 재진입 위험 / 잠금 정상 쌍 | 둘 다 reentrancy-eth | 이 제한된 장부에서 실제 잠금·송금·초기화 순서를 구분 |
| 관리자 전액 회수 | low-level-calls 등 | 예치금과 사용자별 권리 없는 전체 송금을 연결 |

기본 경고는 대회 라벨이 아니다. 경고 개수만으로 정확도를 비교하거나 Slither보다 일반적으로
우수하다고 주장하지 않는다. Slither가 제공한 AST/CFG/SlithIR 기반 위의 자체 판단 계층이다.
새 외부 의존성 설치/소스 복사는 없었다. Slither의 AGPL-3.0 및 원본 표본의 MIT 고지는 유지한다.
9/19 실제 설치본의 고지를 수집했다. 범위와 출처는 [제3자 고지](../THIRD_PARTY_NOTICES.md)에 있으며, 대응 소스 아카이브 전체를 포함한 자료는 아니다.

## 5. 아직 보류하는 것

- 루프, 재귀, assembly, `unchecked`, uint256 외 산술, 일반 외부/라이브러리 호출.
- import 계약 범위/근거 위치, 복수 상속 생성자/생성자 인자, 상태를 바꾸거나 본문 뒤에 동작하는 modifier.
- storage 참조를 인자로 넘기는 내부 함수, 복잡한 반환값/별칭 관계.
- 일반 proxy/업그레이드 안전성, 복잡한 권한/역할 시스템과 다중 자산 DeFi.
- 모든 재진입 유형. 특히 잠금 없는 다른 출금 진입점과 교차 함수/계약 영향은 보류할 수 있다.
- 초기 공급량과 발행 상한의 복잡한 관계, 0 자산/최대 공급량의 실행 가능성, 무시된 checked 계산.
- 상한 값 자체가 바뀌는 모든 복합 수학 관계. 이번 구현은 지원하는 대입/비교 형태만 다룬다.

경로 분석도 제한적이다. 일반 SMT solver/완전한 기호 실행기가 아니다.
함수당 경로 64개, 방문 노드 예산 400, 호출 깊이 8을 넘으면 보류한다.
현재 파일별 60초/전체 540초 예산과 자식 프로세스 종료를 사용한다. 9/19 추가한 1단계 탐지 확장은 철회했지만 시간 설정은 유지한다.
9/18 사용자가 2CPU/4GB 설정에서 개발40을 28.704초에 처리한 결과를 제공했다. 이후 Docker 오프라인 혼합60개 검증도 완료했다. 실제 제출 OS/반입 방법은 주최 측 안내를 따른다.

```bash

```

안전본의 `else` 안 상한 검사를 **별도 사본에서만** 제거해 보고 실행하자.
설명할 질문: “버튼을 누른 사람이 어느 길을 고르면, 어떤 검사를 건너뛰고 쿠폰을 늘릴 수 있나?”

처음에는 paths.py 전체를 외우지 말고, 이 한 쌍의 결과와 근거 줄을 직접 설명하면 된다.


## 9/19 장부 규칙 보강

새 규칙 `src/track1/rules/ledger_operations.py`를 `verdict.py`의 RULES에 등록했다.
기존 공급량 규칙과 별도로 동작하며 총공급량 변수가 없는 전송 장부도 검토한다.

- 생성자의 자기 장부 할당 → 모든 전송/승인/소각 경로를 확인한다.
- 대리 전송은 `[보유자][호출자]`의 승인 한도와 실제 차감량을 연결한다.
- 자기·승인 소각은 잔액과 총량의 동일 감소를 확인한다. 관리자 강제 소각은 타인이 실제 잔액을 가질 경로까지 요구한다.
- 대칭 정지와 관리자 예외, 초기 허용 목록, 관리자 지정 목적지의 두 분기 제약을 구분한다.
- 직접 전송이 없는 경우는 0 초기화·고정 상한·동일량 증가의 폐쇄된 발행 패턴만 정상으로 확인한다. 거래 가능한 자산이라는 주장은 하지 않는다.
- 금고 규칙에는 자기 예치액의 고정 입금 상한과 관리자 선택 수령자/금액의 장부 차감 없는 ETH 지급을 추가했다.

예: `B007`은 직접 transfer와 totalSupply가 없어도 승인 차감 후 잔액이 보존되어 정상 판정할 수 있다.
`M004`는 일반 호출자만 승인을 차감하고 관리자는 우회하므로 위험 판정한다.
승인 함수가 있어도 양수 승인을 만들 수 없거나 초기 수량이 0이면 피해 도달 가능성을 보류한다.

확장한 범위를 넘어서는 쓰기·외부 호출은 보류한다. 수수료 나눗셈, 일반 시간 잠금/struct/루프,
proxy 등은 이번 변경에서 추가하지 않았다. 판정이 쉬워지도록 기존 보류를 일괄 정상으로 바꾸지 않는다.

직접 실습: `tests/fixtures/variants/ledger/delegated.sol`의 승인 차감 한 줄을 별도 사본에서 제거해
승인 재사용 위험으로 바뀌는지 확인하고, 어느 장부가 반복 사용되는지 설명해 보자.

## 9/19 이유와 코드 위치 연결

`reporting.py`가 규칙의 결론과 조건·상태 변경·외부 호출 노드를 받아 이유마다
`[함수, 줄 번호]`를 붙인다. 핵심 위험 노드뿐 아니라 관리자 검사와 설정 경로,
상한 검사도 실제 노드 위치로 연결한다. 정상 결론은 전체 분석 범위를 밝히고,
입력에 없는 소각·정지 기능을 공통 설명으로 언급하지 않도록 장부 규칙 문구를 구분했다.

서로 다른 분기는 성공 경로 번호로 구분하고, 같은 이유/위치의 완전 중복은 제거한다.
보류는 가능한 경우 미지원 연산의 줄을 표시한다. 상세 규칙 실패 로그는 stderr로 보낸다.
이번 설명 개선은 판정 조건을 변경하지 않았으며 위험도·confidence 필드를 추가하지 않았다.
실제 JSON과 주의점은 [판정 근거 읽는 법](REPORTING.md)을 참고한다.

### 후속: 함수별 흐름으로 설명 묶기

조건·대입을 하나씩 나열하던 설명을 권한, 성공 조건, 상태 변화·외부 실행으로 묶었다.
결론과 사용자 영향을 앞에 놓고 초기 설정과 함수별 경로가 이를 뒷받침한다.
외부 호출과 상태 쓰기는 실제 순서를 유지한다. 성공 조건은 경로 전체의 조건이며
모두 상태 변경 전에 실행됐다는 주장이 아니다.

독립 규칙이 반환한 같은 위험 종류와 포함 관계의 자산 쓰기/호출 위치는 같은 컨트랙트
안에서 병합한다. 종류는 규칙에서 직접 전달하는 내부 보고 식별값이며 판정에는 사용하지 않는다.
다른 위험 종류, 독립적인 함수, 한 규칙의 다른 분기는 보존한다. 같은 경로의 중복은
선언 연결·조건식·쓰기·호출 순서·원본 위치로 비교하며 이름/설명 문구 유사도로 판정하지 않는다.
