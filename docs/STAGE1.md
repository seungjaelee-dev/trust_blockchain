# 1단계: 자산 연결이 확인되는 범위 확대

> **철회된 구현의 실험 기록입니다.** 사용자 요청으로 1단계 탐지 확장과 전용 테스트를 제거했습니다. 현재 지원 범위를 설명하는 문서가 아닙니다. 파일별 60초 설정과 별도의 설명 출력 개선은 유지합니다. 같은 합성300개를 재평가했을 때 이전·확장 버전 모두 정답40/오답5/보류255였고 판정 변화가 없었습니다. 아래 내용과 연결된 결과는 철회 전 이력입니다.

2026-09-19 사용자 요청으로 구현했다. yunu의 탐지 아이디어를 참고하되 분석기 복사나 두 분석기의 판정 합산은 하지 않았다. 기존 Slither 선언·경로·장부 분석에 규칙을 추가했고 테스트 소스도 별도로 작성했다. 사용자의 학습/직접 검토 완료를 뜻하지 않는다.

## 구현 범위

| 후보 | 확인하는 조건 | 유지하는 정상·보류 경계 | 구현 파일 |
| --- | --- | --- | --- |
| 공개 무제한 발행 | 외부 호출자가 같은 양을 총량·잔액에 증가, 고정 총량 상한 없음, 양수 전송 가능한 장부 | 고정 총량 상한/0 발행은 정상; 미해석 권한·0 전송만 가능하면 보류 | `expanded_tokens.py` |
| 관리자 직접 몰수 | 초기 자산을 일반 보유자에게 전송 가능, 관리자만 타인 잔액을 0/입력값으로 덮거나 입력량만큼 차감 | 자산 0, 전송 불가, 본인만 변경, 추가 조건은 보류 | `ledger_operations.py` |
| 분기형 전송 제한 | `if (caller != owner)`의 제한 경로와 관리자 우회 경로를 모두 확인, 관리자가 bool 상태 변경 | 관리자에게도 동일 제한이면 악성으로 단정하지 않음; 복잡한 분기 조합은 보류 | `ledger_operations.py` |
| 금고 정지 | 사용자 예치·본인 출금·동일량 장부 차감에 관리 bool 연결 | 대칭 정지는 정상, `!paused || caller == owner` 및 역순은 악성; 제한 없는 별도 출금이 있으면 보류 | `expanded_vaults.py` |
| 장부 미차감 반복 출금 | 본인 장부 전액 또는 그 이하의 입력량을 본인에게 지급, 성공 확인, 장부 변경 없음 | 정상 선행 차감/초기화·제한된 checked 사후 차감은 유지; 0 지급·예치 없음·미해석 조건은 보류 | `expanded_vaults.py` |
| 공개 임의 ETH 송금 | 실제 사용자 예치가 있고 호출자가 수령자·양수 지급량을 선택, 장부 차감 없음 | 예치 없음·0 지급·추가 미해석 권한은 보류; 기존 관리자 임의 송금 지원 유지 | `expanded_vaults.py` |

관리 권한이나 `call` 존재 자체로 악성을 판정하지 않는다. 예를 들어 반복 출금은 **입금으로 장부 증가 → 장부 이하 금액 지급 → 장부 그대로 → 다음 거래에서도 같은 지급**이라는 관계를 확인한다. 재진입이 없어도 발생하는 문제이며, 지급 뒤의 checked 차감으로 중복 지급 전체가 취소되는 기존 정상 경계와 구별한다.

새 규칙의 판정은 기존 집계에 연결되며 외부 JSON은 `file/verdict/reasons/evidence` 네 필드를 사용한다. 지원하지 않는 구조를 일괄 BENIGN으로 바꾸지 않는다.

## 시간 예산

사용자가 알려준 입력 10개 기준으로 파일별 기본 상한을 30초에서 **60초**로 늘렸다. 전체 분석 예산은 **540초**를 유지한다. 10개 모두가 오래 걸리면 평균 가용 시간은 약 54초이며, 뒤쪽 파일은 남은 예산에 의해 중단되거나 미처리 UNCERTAIN으로 반환될 수 있다. 이 설정은 완전한 60초씩의 할당 약속이 아니다.

이 변경은 시간 부족에 의한 보류를 완화한다. 분석 미지원에 의한 보류는 위 규칙 확대가 줄인다. 입력이 크거나 복잡하면 여전히 보류할 수 있다.

## 검증과 재현

`tests/test_stage1.py`는 정상/악성/보류 쌍, 이름 변경·Unicode 주석, 0 자산·0 지급·도달 불가·다른 출금 경로 등의 반례를 검증한다. 기존 공개 표본·확장·장부·보고서·CLI 회귀도 함께 실행한다.

최종 소스와 테스트를 고정한 이미지에서 **38개 테스트 전부 통과, 247.216초**를 확인했다. 새 1단계 테스트는 7개 묶음의 52개 Solidity 입력이며, 파일별 기본 60초/남은 전체 예산 적용을 확인하는 CLI 테스트 1개도 추가했다. [전체 회귀 기록](experiments/stage1-suite.json)에 이미지 ID, 실제 이미지 파일 해시와 로그 해시를 남겼다. 검증 종료 후 현재 소스·테스트·reference와의 해시 차이도 없었다.

`tests/evaluate_stage1_docker.py`는 직접 작성한 대표 10개를 변경 전후 이미지에 넣어 실제 시간, 판정, 원본 schema, 이유·근거 위치, 이미지 ID와 소스 해시를 기록한다. 결과는 [실험 기록](experiments/stage1-integration.json), 상세 입력/출력은 `results/stage1-integration/`에 있다. **선별한 개발셋이며 비공개 정확도나 yunu 대비 일반 성능 측정이 아니다.**

최종 기록된 10개 입력 비교(네트워크 차단, 2 CPU/4GB, 추가 swap 없음):

| 검증 이미지 | 정상 | 악성 | 보류 | 실제 경과 시간 |
| --- | ---: | ---: | ---: | ---: |
| 기존 reporting-review | 2 | 0 | 8 | 13.903초 |
| stage1-review | 3 | 6 | 1 | 16.421초 |

예치 없는 임의 송금 1개는 자산 귀속을 확정하지 못해 보류를 유지했다. 그 외 9개는 검토한 기대 판정과 일치했다. 속도 우열을 측정하는 벤치마크는 아니며 동시 실행 부하에 따라 시간이 달라진다. 실행 시 이미지 내부 소스와 작업 트리의 해시 차이는 없었다.

```bash
python -m unittest discover -s tests -v
python tests/evaluate_stage1_docker.py --image trust404-track1:stage1-review
```

로컬 검증 이미지는 기존 `reporting-review`의 설치된 의존성에 변경 소스를 덧씌워 만들었다. 기본 Dockerfile을 네트워크 없이 처음 재빌드하는 시도는 설치 캐시가 없어 실패했다. 완성 이미지의 실행은 네트워크 없이 검증하며, 배포 환경 최초 빌드의 인터넷 필요 조건은 README와 동일하다. 제출용 태그에 변경 소스를 반영하려면 다시 빌드해야 한다.

## 이번 단계의 한계와 실습

- 복잡한 역할, 여러 자산, claim/escrow/NFT/수수료, 시간·오라클 조건은 추가하지 않았다.
- 직접 몰수와 공개 발행은 양수 자산의 전송 가능성이 단순하게 확인되는 형태만 지원한다.
- 금고의 분기형 관리자 예외, 복잡한 잠금과 정지의 조합, 여러 대체 출금의 전역 가용성 증명은 보류할 수 있다.
- 실제 EVM 공격 트랜잭션을 실행한 검증은 아니다. 정적 분석과 컴파일·CLI 회귀 결과다.

작은 실습: `tests/test_stage1.py`의 `VAULT` 사본에서 `funds[msg.sender] -= amount;`를 제거하고, 같은 출금을 두 거래 연속 호출하면 장부와 ETH가 어떻게 달라지는지 설명해 본다. 원문 `reference/`는 수정하지 않는다.
