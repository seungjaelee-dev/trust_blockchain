# 판정과 실행 흐름 읽는 법

출력은 `file`, `verdict`, `reasons`, `evidence` 네 필드를 유지합니다. `reasons`는 대회 스키마대로 문자열 배열이며 위험도·확률은 추가하지 않았습니다.

## 1. 결론을 먼저 읽고 코드 흐름을 확인하세요

이유 배열의 앞부분은 **판정 근거·사용자 영향**, 뒤는 이를 뒷받침하는 **초기 설정과 함수별 흐름**입니다. 정상 판정은 ‘안전 근거·사용자 영향’으로 시작합니다. 위험이 여러 개면 서로 다른 결론을 먼저 나열합니다.

| 표시 | 읽는 방법 |
| --- | --- |
| 초기 설정 | 배포할 때 관리자·장부·허용 상태 등을 어떻게 정하는가 |
| 권한 | 호출자가 어떤 주소와 같아야 이 경로를 통과하는가 |
| 성공 조건 | 경로가 성공하려면 어떤 조건들이 성립해야 하는가 |
| 상태 변화·외부 실행 | 어떤 값을 바꾸고 누구에게 어떤 호출을 하는가 |
| 판정 근거·사용자 영향 | 이 관계가 사용자에게 왜 위험하거나 지원 범위에서 안전한가 |

코드에 없는 단계를 임의로 채우지 않습니다. 특정 주소와의 직접 동등 검사가 없으면 ‘권한’ 문구가 없을 수 있습니다. 그것만으로 누구나 호출할 수 있다고 주장하지 않습니다. OR 조건 속 관리자 예외는 ‘성공 조건’에 표시됩니다.

**성공 조건이 항상 상태 변경보다 먼저 실행된다는 뜻은 아닙니다.** 뒤쪽 require도 거래 성공을 제한할 수 있습니다. 상태 변화와 외부 호출 사이의 `→`는 해당 작업 순서입니다. ‘송금 → 장부 0 기록’과 ‘장부 0 기록 → 송금’을 구별합니다.

## 2. 실제 P3 출력의 흐름

실제 출력 중 관리자 설정과 전송 설명 두 개를 발췌했습니다. 전체 새 출력은 로컬 `results/sysy-flow.json`, 오프라인 혼합 출력은 [실험 기록](experiments/README.md)에서 확인할 수 있습니다.

```json
"reasons": [
  "[onlyOwner(), 29행 · setWhitelist(address,bool), 32행] 권한: 호출자가 `owner` 주소와 일치; 상태 변화·외부 실행: `whitelist[account]`에 `allowed` 기록.",
  "[transfer(address,uint256), 37, 38, 39, 40, 41행] 성공 조건: `whitelist[msg.sender]` 및 `(to != address(0))` 및 `(value <= balanceOf[msg.sender])`; 상태 변화·외부 실행: `balanceOf[msg.sender]`에서 `value`만큼 차감 → `balanceOf[to]`에 `value`만큼 증가."
]
```

1. **29·32행:** 관리자만 전송 허용 여부를 바꿀 수 있습니다.
2. **37행:** 보내는 사람이 허용 대상이어야 전송할 수 있습니다.
3. **38·39행:** 받을 주소가 0이 아니고 잔액이 충분해야 합니다.
4. **40·41행:** 보내는 잔액을 줄이고 받는 잔액을 늘립니다.
5. **사용자 영향:** 배포자는 처음부터 허용됩니다(22·25행). 받는 사람의 허용 여부는 전송 조건이 아니므로, 일반 사용자는 받을 수 있지만 관리자가 허용하지 않으면 다시 보낼 수 없습니다. 이 관계가 첫 판정 요약에 나옵니다.

예전에는 같은 위험을 세 번 요약하고 대입 하나하나도 별도 이유로 출력했습니다. 이제 P3는 **결론 → 초기 설정 → 관리자 설정 경로 → 사용자 전송 경로**의 총4개 이유입니다. 공개5개의 이유 수는 P1 17→5, P2 8→3, P3 14→4, P4 13→5, P5 6→4입니다. 이유 수를 강제로 제한한 결과가 아닙니다.

## 3. 이유와 evidence 연결

`reasons[0]`과 `evidence[0]`이 짝이라는 뜻은 아닙니다. 이유 앞의 **함수명과 줄 번호**가 연결 고리입니다. 한 이유가 여러 줄의 관계를 설명하므로 근거도 여러 개일 수 있습니다. 같은 위치는 evidence에 한 번만 나옵니다.

줄 번호는 입력 첫 줄을1로 센 값입니다. 여러 줄에 걸친 구문은 Slither 노드의 시작 줄을 사용합니다. modifier에서 검사하면 실제 modifier 위치를 표시합니다. 함수 밖 초기값은 `[상태 선언, 7행]`처럼 나옵니다.

`[컨트랙트 전체 분석]`은 지원 범위의 전체 경로를 검토한 결론입니다. ‘다른 자산 이동 경로가 없다’는 주장을 특정 한 줄로 증명했다고 표시하지 않습니다.

## 4. 무엇을 합치고 무엇을 남기는가

- 같은 컨트랙트의 독립 규칙들이 **같은 위험 종류와 포함 관계가 있는 상태 변경·호출 위치**를 확인하면 중복 결론을 합칩니다. 위험 종류는 규칙이 전달한 내부 식별값입니다. 파일명·변수명·설명 문구의 유사도로 추측하지 않으며 판정에도 사용하지 않습니다.
- 독립 규칙 하나가 지원 범위의 컨트랙트 전체 안전성을 확인했다면 겹치는 정상 결론은 하나로 제시합니다. 확인한 함수별 사실과 근거는 함께 보존합니다.
- 동일 경로는 선언·연산·조건·원본 위치·호출 순서로 비교합니다. `a >= b`와 `b <= a`는 같은 표현으로 정규화합니다.
- 서로 다른 위험 종류, 독립 함수, 같은 규칙에서 반환한 서로 다른 분기는 유지합니다. 문장이 비슷하다는 이유로 삭제하거나 ‘최대3개’ 같은 제한을 두지 않습니다.
- 분기가 여러 개면 성공 경로 번호를 표시합니다. 경로1과 경로2의 조건을 한 번의 실행에 모두 적용해서 읽으면 안 됩니다.

수집하는 것은 규칙이 반환한 발견입니다. 기존 금고 규칙 등의 우선 반환 구조는 유지합니다. 모든 가능한 취약점을 빠짐없이 열거한다는 뜻은 아닙니다.

## 5. UNCERTAIN은 어떻게 읽는가

미지원 연산의 노드를 확보하면 해당 줄과 분석 한계를 표시합니다. 컴파일 실패·시간 초과로 위치를 확보하지 못하면 `[컴파일·구조 분석]`이나 `[분석 실행]`으로 표시합니다. 줄 번호나 사용자 피해를 지어내지 않습니다. 자세한 도구 오류는 stderr 로그에 있습니다.

설명 정리는 분석 지원 범위를 늘리는 작업이 아닙니다. 보류를 줄이려면 실제 사례의 연산·조건·자산 흐름을 별도로 검토해야 합니다.

## 6. 구현과 검증

```text
Slither 코드 노드 → 경로 해석(조건·상태 변경·호출 순서)
  → rules/*.py: 판정과 발견 종류·핵심 위치
  → reporting.explain(): 결론과 경로 설명을 내부 보고서로 구성
  → verdict.py → reporting.merge_reports(): 컨트랙트별 중복 병합
  → reporting.render(): 이유 문자열과 evidence 생성
  → cli.py: 파일 결과들을 JSON 배열 하나로 출력
```

내부 보고서는 JSON에 노출하지 않습니다. 공개 표본의 중복 요약, 이름 변경·Unicode 줄 이동, 상한 검사, 미지원 나눗셈, 한 컨트랙트의 세 위험 경로, 여러 컨트랙트의 독립 위험, 재진입 호출/초기화 순서를 테스트합니다. 실행 결과는 [실험 기록](experiments/README.md)에 보존합니다.

위치 대응 검증은 모든 Solidity 프로그램의 설명을 자동 증명한 것은 아닙니다. 개발 표본의 결과를 비공개 성능으로 확대하지 않습니다.

실습: `reference/public/P3_Honeypot.sol` 사본에서 함수 이름을 바꾸거나 빈 줄 두 개를 추가해 분석하세요. 판정은 유지되고 함수명과 줄은 실제 입력에 맞게 바뀌어야 합니다. 이어 ‘받을 수 있지만 다시 보내지 못하는 이유’를 코드와 함께 설명해 보세요.
