# 판정 근거 읽는 법

JSON의 네 필드 `file`, `verdict`, `reasons`, `evidence`를 유지합니다. 위험도 점수나 확률은 추가하지 않았습니다. 이번 변경은 설명과 위치 연결이며 판정 조건을 바꾸지 않았습니다.

## 1. 이유와 위치를 연결하기

`reasons[0]`과 `evidence[0]`이 짝이라는 뜻은 아닙니다. **이유 앞의 대괄호에 적힌 함수와 줄 번호**가 연결 고리입니다. 줄은 입력 파일의 첫 줄을 1로 셉니다. 여러 줄에 걸친 구문은 Slither 노드의 시작 줄입니다.

실제 `ledger_admin_exemption.sol` 결과 중 일부입니다. 전체 출력은 [혼합 60개 결과](experiments/reporting-integration.json)에 있습니다.

```json
{
  "file": "ledger_admin_exemption.sol",
  "verdict": "MALICIOUS",
  "reasons": [
    "[onlyAdmin(), 12행] 호출자가 `admin`와 같은 주소일 때만 이 경로로 진입할 수 있습니다.",
    "[setPaused(bool), 14행] 상태 변경: `paused`에 `value`를 기록합니다.",
    "[transfer(address,uint256), 17행] 분석한 성공 경로의 조건: `(!(paused) || (msg.sender == admin))`.",
    "[transfer(address,uint256), 19행] `balanceOf[msg.sender]`를 `amount`만큼 차감합니다.",
    "[transfer(address,uint256), 20행] `balanceOf[to]`를 `amount`만큼 증가합니다."
  ],
  "evidence": [
    {"function": "onlyAdmin()", "line": 12},
    {"function": "setPaused(bool)", "line": 14},
    {"function": "transfer(address,uint256)", "line": 17},
    {"function": "transfer(address,uint256)", "line": 19},
    {"function": "transfer(address,uint256)", "line": 20}
  ]
}
```

쉬운 말로 읽으면:

1. **12행:** 관리자만 정지 버튼을 조작할 수 있다.
2. **14행:** 그 버튼으로 정지 상태를 바꾼다.
3. **17행:** 전송하려면 ‘정지되지 않았거나, 내가 관리자’여야 한다. `!`는 반대, `||`는 ‘또는’이다. 그래서 관리자는 정지 중에도 통과한다.
4. **19~20행:** 통과하면 실제로 보내는 사람의 잔액을 줄이고 받는 사람의 잔액을 늘린다.
5. 따라서 단순히 `paused`라는 이름이 있어서가 아니라, **관리자가 정지 상태를 바꾸고 자기만 전송할 수 있는 흐름**을 확인해서 위험으로 판정한다.

실제 출력 첫 이유에는 이 결론과 관련 위치들을 함께 제시합니다. 뒤의 개별 문장은 결론을 뒷받침하는 코드 사실입니다. 개별 대입이나 검사 자체가 모두 취약점이라는 뜻은 아닙니다.

## 2. 여러 이유와 분기

- 독립적인 위험이 여러 개 확인되면 해당 이유들을 모읍니다. 첫 번째 이유만 출력하지 않습니다.
- 이유 하나가 권한 검사와 자산 이동 등 여러 위치를 연결할 수 있습니다.
- 같은 위치는 `evidence`에 한 번만 남깁니다. 문구도 완전히 같은 경우만 중복 제거합니다. 비슷해 보여도 서로 다른 규칙의 설명은 남을 수 있습니다.
- 같은 함수의 여러 성공 경로는 ‘성공 경로 1’, ‘성공 경로 2’로 구별합니다. 서로 반대인 조건이 나오더라도 한 번의 실행에 두 조건이 동시에 필요하다는 뜻이 아닙니다. 경로 번호는 설명용이며 원본 소스의 번호가 아닙니다.

여기서 수집하는 것은 각 규칙이 반환한 위험입니다. 모든 잠재적 취약점을 빠짐없이 열거한다는 뜻은 아닙니다. 예를 들어 현재 금고 규칙은 임의 코드 실행·임의 지급·전체 회수·재진입 순으로 우선 결론을 반환합니다. 이번에는 이 탐지 우선순위를 바꾸지 않았습니다.

## 3. 줄 번호가 없는 이유

`[컨트랙트 전체 분석]`은 지원 범위의 모든 경로를 검토한 결론입니다. ‘다른 자산 이동 경로가 없다’는 결론을 특정 한 줄만으로 증명했다고 표시하지 않습니다. 함수 밖의 초기값 위치는 `[상태 선언, 7행]`처럼 표시합니다.

`UNCERTAIN`에서 미지원 연산의 노드를 확보했다면 그 줄을 표시합니다. 컴파일 실패나 시간 초과로 위치를 확보하지 못했다면 `[컴파일·구조 분석]` 또는 `[분석 실행]`으로 표시하고 줄 번호를 꾸며내지 않습니다. 상세 도구 오류는 stderr 로그에서 확인합니다. 분석하지 못했다는 말은 안전하다는 뜻이 아닙니다.

## 4. 코드에서는 어떻게 만드는가

```text
Slither의 실제 코드 노드
  → rules/paths.py: 경로별 조건·상태 변경·외부 호출과 노드 보존
  → rules/*.py: 위험/안전 판단과 핵심 근거 선택
  → reporting.py: Claim(설명, 근거 노드) 생성
  → render(): 대괄호 위치 설명 + evidence 생성
  → verdict.py: 여러 규칙·컨트랙트 결과 집계, 중복 제거
  → cli.py: 파일 결과들을 JSON 배열로 출력
```

`reporting.py`는 이름으로 위험을 추측하지 않습니다. 분석기가 이미 추적한 선언·연산을 사람이 읽을 식으로 표시합니다. 예를 들어 실제 증가량과 상한 검사를 확인한 노드에서 `((totalSupply + amount) <= MAX_SUPPLY)`라는 설명을 만듭니다. 출력용 변환은 판정에 사용하지 않습니다.

위험 결론은 관련 검사·변경 노드와 연결합니다. 정상 결론은 전체 분석 문장에 이어 실제 검사와 변경 사실을 제시합니다. 미지원 메시지는 가능한 경우 위치를 가진 한계를 우선 제시하고, 규칙별 상세 실패는 진단 로그로 분리합니다.

## 5. 검증 범위와 작은 실습

오프라인 Docker에서 공개5·개발40·장부14·문법 오류1의 총60개를 검증했습니다. 이전 결과와 판정이 모두 같고, schema·이유의 위치와 evidence 연결·위치 범위·중복 제거를 확인했습니다. 별도 회귀 테스트는 이름 변경, Unicode 주석 및 줄 이동, 반대 분기, 상한 검사, 권한 검사, 미지원 나눗셈 위치를 확인합니다.

이는 모든 Solidity 코드에서 모든 설명의 의미를 증명한 것은 아닙니다. 지원 밖의 구조는 보류하며 이 개발 데이터의 결과를 비공개 성능으로 확대하지 않습니다.

실습: `tests/fixtures/variants/ledger/admin_exemption.sol`을 별도 폴더에 복사한 뒤 맨 위에 빈 줄 두 개를 넣어 분석해 보세요. 판정은 같고 근거 줄은 2씩 증가해야 합니다. 이어 17행에 있던 조건을 본인의 말로 설명해 보세요.
