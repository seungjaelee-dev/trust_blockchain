## 첫 분석 범위

### R1 공급량 증가와 상한
P2/P4 대비. 외부 실행 경로, 소유자 검사 실제 의미, 공급량·잔액 증가, 입력값 의존성을 확인한다.
상한이 증가 이전의 모든 해당 경로에서 강제되는지, 같은 증가량을 검사하는지,
상한이 고정인지, 우회 가능한 다른 쓰기 경로가 있는지 본다.
uint256의 표현 범위/overflow 검사가 토큰의 경제적 발행 상한이라는 뜻은 아니다.
P1의 생성자 초기 공급량은 반복 실행 가능한 발행 경로와 구분한다.

### R2 비대칭 전송 제한
P3의 발신자 whitelist 검사, 생성자의 소유자 허용, 소유자만 목록 수정 가능을 연결한다.
전송 제한이 소유자에게도 대칭적으로 적용되는 정상 경계와 비교한다.
이름만 whitelist이고 실제로 사용하지 않는 변수는 근거가 아니다.

### R3 임의 delegatecall
P5의 deposit으로 사용자 자산이 들어오고 owner가 target/data를 제어하는 execute를 통해
현재 컨트랙트 저장소 문맥에서 코드를 실행할 수 있음을 연결한다.
delegatecall 문자열만 찾지 않는다. 고정 대상·도달 불가 경로·예치 없는 상태는 별도 분석한다.
보호된 proxy 등 미지원 복잡한 경우는 대회 규칙과 분석 범위를 고려해 UNCERTAIN으로 남긴다.

### BENIGN과 UNCERTAIN
위험 미탐지 = BENIGN이 아니다. 함수/컨트랙트 범위, 외부 호출, 상태 쓰기 중 미해결 항목을 수집한다.
P1/P4의 안전 근거를 확인하되 파일명·코드 해시 allowlist로 처리하지 않는다.
작은 분석기는 보류가 많을 수 있다. coverage를 숨기지 않고 근거의 정확성을 우선한다.
새로운 비공개 패턴은 예상만 할 뿐 결과를 알 수 없다.

## 오프라인 반입

개발 중에는 공식 자료와 패키지를 받을 수 있다. 채점 실행에서는 설치/다운로드가 없어야 한다.
원문은 2 vCPU/4GB/10분을 명시하지만 OS/아키텍처·이미지 반입 절차는 별도 확인이 필요하다.
Docker는 의존성 포함 환경을 묶는 한 방법이며 필수는 아니다.
컨테이너를 선택한다면 이미지까지 준비해 network none으로 실행하고 digest를 기록한다.
Dockerfile만 제공하거나 실행 중 docker pull/pip install/solc 다운로드를 하는 방식은 충분하지 않다.
다른 경로를 선택하면 해당 OS의 런타임·컴파일러·의존성을 실제 반입 방식에 맞게 포함한다.
개발환경의 설치 캐시가 있어 성공한 것을 깨끗한 환경의 오프라인 성공으로 오인하지 않는다.

## 최소 평가

- 입력 5개 → 출력 객체 5개, 대문자 enum, 원본 기준 evidence.
- 주석/파일명/함수명/지역 변수 이름 변경 후 의미 유지.
- 상한 제거/검사 우회/소유자 대칭 제한 등은 사람이 의미를 확인하고 기대 결과 작성.
- 같은 파일의 변형은 train/test 독립 표본처럼 세지 않는다. ML은 초기 범위 밖.
- malformed .sol·미지원 compiler·timeout은 파일별 UNCERTAIN, 나머지는 정상 진행.
- stdout 오염/빈 배열/중복 basename/원본명 매칭/schema 검증.
- baseline 경고와 자체 verdict의 차이, 오탐·미탐·보류 이유.

## 사용자의 학습과 포트폴리오

매 세션 코드 흐름 15~20분, 구현/확인 100~120분, 사용자 변형 실습·기록에 나머지 시간을 둔다.
문법 전 범위를 선행하지 않는다. msg.sender, modifier, mapping, require 등 당일 코드의 의미를 익힌다.
구조 추출 도구의 기여와 본인 규칙/판정/실험의 기여를 구분한다.
연구실에 보여줄 핵심은 코드 줄 수보다 '왜 이런 판정을 했고, 어떤 반례에서 실패했으며, 어떻게 고쳤는가'다.
소스만 분석하는 도구가 실제 배포된 주소의 코드와 일치함을 증명하지는 않는다. 지갑 연동은 별도 확장이다.
