# 제출 마무리 계획

2026-09-19 기준. 목표 제출일은9/20이며 공식 마감 시각·전달 형식은 주최 측 공통 안내로 확인한다.

## 완료한 항목

- 디렉터리 CLI, schema 출력, 오류 격리, 파일별60초/전체540초 예산과 자식 프로세스 종료.
- 공개/개발 변형, 장부·금고 지원 확대, 함수별 흐름 설명과 근거 연결.
- 현재 코드의 전체31 테스트와 혼합60개 검증 통과. [제출 검증](experiments/submission-check.json)에 기록했으며 철회 전 1단계 실험과 구분한다.
- 실제 설치된 의존성/solc/기본 이미지의 고지 수집, 제출용 개발 지침과 문서 정리.
- 기록: [실험 목록](experiments/README.md), [진행 이력](PROGRESS.md).

## 최종 전달 순서

1. README와 지원 한계, 고지문을 검토하고 필요한 소스·테스트·문서·실험 JSON의 Git 포함 여부를 확인한다.
2. 최종 commit을 만들고 그 commit으로 제출용 이미지를 빌드한다. 변경이 있으면 관련 검증을 다시 수행한다.
3. [제출 안내](SUBMISSION.md)에 따라 commit ID, 이미지 ID와 tar SHA256을 기록한다.
4. 주최 측이 지정한 저장소/이미지/압축본 전달 방식으로 제출한다. 오프라인 환경에 Dockerfile만 전달하지 않는다.
5. 바이너리 전달 시 고지문과 해당 버전의 소스 취득 경로를 함께 제공한다. 필요한 소스 아카이브의 전달 범위는 THIRD_PARTY_NOTICES.md에 구분한다.

원격 push, 제출 태그/commit 생성, 최종 이미지 tar 전달은 사용자 요청에 맞춰 수행한다.
웹 UI·새 규칙 확대·새로운 전체 데이터 실험은 최종 제출 정리의 필수 작업이 아니다.

## 완료 기준

- 전달된 고정본이 README 명령만으로 오프라인 디렉터리 분석을 수행한다.
- 출력에는 입력 파일마다 결과 하나가 있고 stderr와 JSON이 분리된다.
- 실제 실행 기록과 고정본 식별값을 연결한다. 개발 데이터 성능을 비공개 성능으로 표현하지 않는다.
- 공개 표본 한 쌍의 권한→조건→상태 변화→영향을 코드 위치와 함께 설명할 수 있다.

기술 참고: [Slither](https://github.com/crytic/slither), [detector 가이드](https://github.com/crytic/slither/wiki/Adding-a-new-detector).
