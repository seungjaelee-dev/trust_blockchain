01

먼저, 이 프로그램은 무엇을 할까?

계약은 돈을 다루는 자판기의 규칙집이라고 생각해 보세요.

① 설계도입력 폴더의 .sol
→
② 구조 읽기solc + Slither
→
③ 의미 검사우리의 일곱 규칙
→
④ 판정표이유 + 원본 위치

예를 들어 “주인만 새 쿠폰을 만들 수 있다”는 문장이 있습니다. 검사기는 여기서 멈추지 않습니다. 얼마나 만들 수 있는지, 남에게 보낼 수 있는 쿠폰인지, 다른 사람이 가진 쿠폰에 어떤 영향을 주는지까지 연결합니다.

위험 근거를 찾음

MALICIOUS

대회 기준에 해당하는 위험을 코드 근거로 설명할 수 있습니다.

지원 범위에서 확인

BENIGN

지원하는 계약 모델의 안전 조건을 확인했습니다. 모든 종류의 보안 문제에 대한 보증은 아닙니다.

판단에 필요한 확인 부족

UNCERTAIN

읽지 못한 구조, 실패한 컴파일, 시간 초과 등으로 확정하지 못했습니다.

역할을 세 덩어리로 기억하세요.

cli / worker는 검사소 운영, rules는 의미 검사, verdict / reporting은 결론과 설명입니다. solc와 Slither는 코드 구조를 얻는 기반 도구입니다.

실제로 블록체인에 올리고 돈을 보내 보는 건가요?

아닙니다. 현재 분석기는 코드를 컴파일하고 구조를 읽는 정적 분석을 합니다. 계약을 블록체인에 배포하거나 공격 거래를 실행하지 않습니다. “이 조건으로 이 길을 지나면 이런 상태 변화가 생긴다”를 지원하는 형태 안에서 추적합니다.

Slither의 기본 경고 개수를 대회 판정으로 바꾸지도 않습니다. Slither가 제공한 구조를 우리 규칙이 읽고 자산·권한·상한의 관계를 판단합니다.

02

파일 한 장의 여행

아래 순서가 실제 호출 흐름입니다. 코드가 궁금할 때만 펼쳐 보세요.

8단계를 이어서 읽습니다. 위 버튼으로 한 단계에 집중할 수 있습니다.

입구로 들어옵니다

scripts/analyze.py가 cli.main()을 부릅니다. 여기서 “어느 폴더를 검사할지”를 명령 인자로 전달합니다.

입력 폴더 경로 → cli.main()

실제 코드 펼치기 · analyze.py
scripts/analyze.py · 6–12행 · 현재 파일 발췌
6sys.path.insert(0, str(Path(__file__).resolve().parents[1] / "src"))78from track1.cli import main910if __name__ == "__main__":11    raise SystemExit(main())12

import는 다른 파일의 기능을 가져오는 문법입니다. main()을 부르면 실제 접수가 시작됩니다. SystemExit는 main이 돌려준 종료 번호를 운영체제에 전달합니다.

명단을 만들고, 시간을 나눕니다

cli.py는 폴더 바로 아래의 .sol 파일을 이름순으로 정렬합니다. 먼저 전부 보류 상태로 준비한 뒤 하나씩 실제 결과로 교체합니다. 도중에 시간이 끝나도 명단에서 파일이 사라지지 않게 하기 위해서입니다.

파일 목록 → run_file(source, solc, 허용 시간)

실제 코드 펼치기 · cli.py
src/track1/cli.py · 111–116행 · 현재 파일 발췌
111    results = [112        uncertain(p, "전체 시간 예산 소진으로 이 파일은 분석하지 못했습니다.")113        for p in files114    ]  ## 일단 uncertain(시간소진)으로 두기115    solc = args.solc.expanduser().resolve()116    if not solc.is_file() or not os.access(solc, os.X_OK):

results는 결과들을 담는 목록입니다. uncertain(p, ...)는 파일 p에 대한 보류 결과 한 개를 만듭니다. 이 초기값은 “악성일 것 같다”는 추측이 아니라 미처리 파일을 위한 자리표입니다.

파일마다 별도 검사실을 엽니다

run_file()은 별도 Python 프로세스로 worker.py를 실행합니다. 임시 폴더를 작업 공간으로 쓰고, 허용 시간을 넘으면 자식 프로세스 그룹까지 종료합니다. 한 파일의 실패를 나머지 파일과 분리합니다.

부모 CLI → 별도 worker 프로세스 + 임시 result.json 경로

실제 코드 펼치기 · cli.py
src/track1/cli.py · 41–47행 · 현재 파일 발췌
41        process = subprocess.Popen(42            [sys.executable, str(worker), str(source), str(solc), str(output)],43            cwd=directory,44            stdout=sys.stderr,45            stderr=sys.stderr,46            start_new_session=True,47        )

Popen은 별도 프로그램을 시작합니다. worker가 받는 것은 소스 경로·컴파일러 경로·결과를 쓸 경로입니다. start_new_session은 이 검사실의 프로세스들을 함께 관리하기 위한 설정입니다.

글자를 구조와 길 지도로 바꿉니다

worker.analyze_file()에서 solc와 Slither를 사용합니다. 함수·변수 선언·갈림길·계산·호출을 구조로 읽어 verdict.analyze()에 넘깁니다.

.sol 텍스트 → Slither 분석 객체 → verdict.analyze()

실제 코드 펼치기 · worker.py

계약마다 일곱 검사를 시도합니다

verdict.py는 파일 안의 각 계약에 규칙을 차례로 시도합니다. 각 규칙은 자신이 이해하는 계약 모양인지 확인하고 조건·잔액·호출을 검사합니다. 지원하지 못하면 Unsupported로 알립니다.

계약 구조 → 각 rule(contract) → 판정 또는 지원 한계

실제 코드 펼치기 · verdict.py
src/track1/verdict.py · 28–33행 · 현재 파일 발췌
28        for label, rule in RULES:29            try:30                matched.append(rule(contract))31            except Unsupported as error:32                missing.append((label, str(error), error.node))33        if matched:

rule은 지금 시도할 분석 함수입니다. matched에는 성공한 규칙의 결과가 모입니다. Unsupported를 받았다고 바로 파일 전체를 보류하지는 않습니다. 다른 규칙이 계약을 완전히 설명할 수 있는지도 봅니다.

위험 근거와 미해결 범위를 모읍니다

분석 범위 검사를 통과한 뒤, 위험 근거가 있으면 M, 위험 근거는 없지만 미해결 계약이 남으면 U, 필요한 계약을 지원 모델로 확인했으면 B가 됩니다. 규칙들의 다수결이 아닙니다.

계약별 결과와 한계 → 파일별 verdict

근거를 읽을 수 있는 문장으로 만듭니다

reporting.py는 규칙의 결론을 초기 설정, 권한, 성공 조건, 상태 변화·호출 순서와 연결합니다. 규칙 실행 중 설명 재료를 만들고, 집계할 때 중복을 정리합니다. 실제 구현에서는 5~6단계에서도 함께 사용됩니다.

결론 + 경로 기록 + 원본 노드 → reasons / evidence

03

복잡한 코드를 어떻게 기억할까?

검사기는 코드를 읽으며 “조건 / 바뀐 것 / 외부 호출”을 메모합니다.

학습용 축약 예시 · 실제 분석 출력 아님

친구에게 쿠폰 3장 보내기

require(balance[msg.sender] >= 3);
balance[msg.sender] -= 3;
balance[friend] += 3;

내가 10장을 갖고 있었다면 7장이 됩니다. 친구가 2장을 갖고 있었다면 5장이 됩니다. 두 사람의 합계 12장은 그대로입니다.

분석기가 남기는 메모

기록이 예시에서의 뜻
guards성공하려면 내 잔액이 3 이상
writes내 잔액 −3, 친구 잔액 +3
calls이 예시에는 외부 호출 없음

실제 숫자를 모르면 “이전 잔액 − amount”처럼 관계를 저장합니다. 이를 기호 표현이라고 부릅니다.

linear.py: 한 줄로 이어진 길

지원하는 단순 함수의 실행 노드를 순서대로 읽습니다. 읽을 수 없는 갈림길이나 반복이 나오면 범위를 벗어났다고 알립니다.

첫 네 규칙이 사용하는 기본 해석 도구

paths.py: 갈림길이 있는 지도

if의 참·거짓 길을 나눠 조건과 기록을 따로 보관합니다. 지원하는 내부 함수 호출은 인자를 연결해 따라갑니다. 실패로 취소되는 길은 성공 경로에서 제외합니다.

확장 토큰·금고·장부 규칙의 경로 해석 도구

실제 코드 펼치기 · linear.py
src/track1/rules/linear.py · 34–36행 · 현재 파일 발췌
34def symbol(variable):35    return ("variable", variable)36

같은 이름표를 붙인 다른 사물은 다른 사물입니다. 변수도 이름 문자열만 보지 않고 Slither의 선언 객체와 연결합니다. 이름을 balance에서 bananas로 바꿨다는 이유만으로 의미가 달라지지 않게 하기 위해서입니다.

src/track1/rules/paths.py · 64–74행 · 현재 파일 발췌

Path는 길 하나의 메모장입니다. guards는 성공 조건, writes는 저장소 변경, calls는 외부 호출, steps는 진행 순서입니다. values/refs/storage는 값과 참조를 추적하는 내부 기록입니다.

왜 require가 뒤에 있어도 확인해야 하나요?

Solidity에서 실행이 revert로 끝나면 그 실행의 상태 변경도 되돌아갑니다. 따라서 “총량을 더한 뒤 상한 검사”라는 순서만 보고 바로 상한 우회라고 할 수는 없습니다. 성공한 실행이 결국 상한을 넘을 수 있는지를 봐야 합니다.

외부 호출이 끼면 다른 코드가 중간에 다시 들어올 수 있어 금고 규칙의 추가 검토가 필요합니다. 보고서의 “성공 조건”은 항상 코드 맨 앞에서 검사됐다는 뜻이 아닙니다.

지도에는 읽을 수 있는 크기가 있습니다.

경로 예산 64, 호출 깊이 8, 노드 방문 예산 400 등의 제한이 있습니다. 루프·재귀·assembly·복잡한 외부 호출까지 일반적으로 풀어 주는 분석기는 아닙니다. 무시한 계산이 실행을 취소할 수 있는지도 checked.py에서 제한적으로 확인합니다.

04

주인이 쿠폰을 만드는 두 계약

공개 표본 P2와 P4로 “관리자 권한”과 “위험한 권한”의 차이를 봅니다.

P2 · MALICIOUS

개수를 막는 천장이 없다

관리자가 총량과 자기 잔액을 같은 양만큼 늘립니다. 그 잔액은 다른 사람에게 보낼 수 있습니다. 총공급량에 대한 정책상 상한이 없어 기존 보유자의 비중을 희석할 수 있습니다.

실제 코드 펼치기 · P2_HiddenMint.sol
reference/public/P2_HiddenMint.sol · 30–34행 · 현재 파일 발췌
30    function distributeRewards(uint256 amount) external onlyOwner {31        totalSupply += amount;32        balanceOf[owner] += amount;33        emit Transfer(address(0), owner, amount);34    }

+= amount는 이전 값에 amount를 더해 다시 저장한다는 뜻입니다. 이름이 distributeRewards여서 위험한 것이 아닙니다. onlyOwner의 실제 조건, 공급량·잔액 증가, 전송 기능을 함께 확인합니다.

P4 · BENIGN

새 총량이 천장 아래여야 한다

관리자는 발행할 수 있지만 총량 + 이번 양 ≤ MAX_SUPPLY를 통과해야 합니다. 고정 상한과 초기 상태, 다른 상태 변경까지 지원 모델에 맞는지 확인합니다.

실제 코드 펼치기 · P4_CappedMint.sol
reference/public/P4_CappedMint.sol · 24–31행 · 현재 파일 발췌
24    function mint(address to, uint256 amount) external onlyOwner {25        require(to != address(0), "zero address");26        require(totalSupply + amount <= MAX_SUPPLY, "cap exceeded"); // 총공급량 상한을 강제합니다.27        totalSupply += amount;28        balanceOf[to] += amount;29        emit Mint(to, amount);30        emit Transfer(address(0), to, amount);31    }

require(조건)은 조건이 거짓이면 실행을 취소합니다. 현재 총량에 새 수량을 더한 값을 검사하므로 한 번의 발행량만 검사하는 것과 다릅니다. 상수 선언과 다른 함수도 실제 분석 대상입니다.

“이 함수에 검사 한 줄이 보인다”만으로 끝나지 않습니다.

다른 발행 버튼이 상한을 피할 수 있는지, 상한 자체를 마음대로 바꿀 수 있는지, 초기 상태와 정수 계산이 맞는지까지 지원하는 범위에서 연결해야 합니다. uint256의 자료형 최대치는 이 대회에서 말하는 의미 있는 발행 상한과 다릅니다.

토큰과 ETH 금고는 무엇이 다르죠?

토큰: 계약 안의 잔액 장부가 쿠폰 자체입니다. 전송은 보내는 장부를 줄이고 받는 장부를 늘립니다.

ETH 금고: 장부에는 “내가 찾아갈 권리”가 적혀 있고, ETH 송금은 별도로 일어납니다. 장부만 줄고 돈이 안 나가거나, 돈은 나갔는데 장부가 남아 있으면 두 기록이 어긋납니다. 그래서 외부 송금과 장부 변경 순서를 함께 읽습니다.

그럼 Python 규칙은 어디서 이것을 연결할까?

일곱 규칙은 무엇을 검사할까?

각 규칙은 계약 전체가 자신의 지원 모델에 맞는지도 확인합니다.

일곱 단계의 필터를 모두 통과해야 정상인 구조가 아닙니다. 여러 형태의 계약을 읽기 위한 일곱 분석 함수입니다. 한 규칙이 해당 계약을 충분히 설명한다면 다른 규칙의 형태 불일치가 자동으로 보류를 만들지는 않습니다.

판단하는 것: 상한 없는 관리자 발행은 M. 실제로 강제되는 고정 상한은 지원 모델의 다른 조건까지 맞으면 B.

owner가 있다는 사실만으로 M이 되지 않습니다.

언제 확정하고, 언제 보류할까?

UNCERTAIN은 원인을 나눠 읽어야 합니다.

상황파일 결론왜?
분석 중 충분한 위험 근거 발견MALICIOUS다른 계약의 한계가 남아도 이미 발견한 위험 근거를 보존
위험 근거 없음 + 미해결 계약 있음UNCERTAIN일부 정상 결과만으로 파일 전체를 설명할 수 없음
필요한 계약을 지원 모델로 안전 확인BENIGN미해결 범위 없이 해당 모델의 안전 조건 확인

위 표는 계약 분석·집계 단계의 흐름입니다. import 계약의 원본 범위를 지원하지 않는 경우는 집계 전에 U로 반환합니다. 구체 계약에서 해석되는 추상 기반 계약은 별도 미해결 계약으로 중복 취급하지 않습니다. 판정할 계약이 없으면 U입니다.

학습용 판정 실습 · Solidity 실행 아님

한 파일에 계약이 두 개라면?

내용을 읽지 못한 보류

계약이 지원 모델에 맞지 않거나 반복문·복잡한 자산 관계·미지원 연산이 등장한 경우입니다. 이때 시간을 늘려도 읽는 능력 자체가 생기지는 않습니다.

확인할 곳: verdict.py의 한계 설명 → 해당 규칙 → paths.py 또는 linear.py

실행을 끝내지 못한 보류

컴파일 실패, solc 실행 불가, 파일 시간 초과, 전체 예산 소진 등입니다. 환경과 실행 진단부터 확인해야 합니다.

확인할 곳: reasons의 실행 사유 → stderr → worker.py와 cli.py

보류를 줄이려면 무엇이 달라져야 할까요?

미지원 구조라면 경로 해석과 규칙의 지원 모델을 실제로 넓히고 정상·악성 경계를 함께 검증해야 합니다. 보류 문구를 정상으로 바꾸거나 협업자 판정을 합산하는 것만으로 근거가 생기지는 않습니다. 이 안내서는 현재 분석 로직을 변경하지 않습니다.

규칙 하나가 Unsupported면 전체 UNCERTAIN 아닌가요?

예를 들어 고정 공급 토큰이 “발행 규칙”의 모양에 안 맞는 것은 자연스럽습니다. 다른 규칙이 그 계약의 전체 지원 모델을 확인했다면 그 결과를 쓸 수 있습니다.

하지만 계약 A는 정상으로 설명하고 계약 B는 어느 규칙도 설명하지 못했다면, 위험 근거가 없는 한 파일 전체는 U입니다. 규칙의 형태 불일치와 계약의 미해결 범위는 다릅니다.

08

시간과 결과는 누가 지킬까?

분석 내용만큼, 끝까지 유효한 판정표를 내는 일도 중요합니다.

기본 실행 예산

파일 최대 60초 / 전체 540초

파일 10개라면 평균 1분쯤이라는 감은 맞지만, 10개 모두에게 60초를 보장하지는 않습니다. 다음 파일의 허용 시간은 min(60, 전체 남은 시간)입니다.

540초는 전체 10분 한도 안에서 출력·정리 여유를 두기 위한 기본 예산입니다. 각 파일은 실제로 더 빨리 끝날 수 있고 전체 시간에는 준비·정리 비용도 들어갑니다.

시간 배분 실습 · 실제 타이머 아님

파일별 설정은 기본 60초로 고정한 학습 예시입니다.

실제 코드 펼치기 · cli.py
src/track1/cli.py · 133–133행 · 현재 파일 발췌
133            results[index] = run_file(source, solc, min(args.file_timeout, remaining))

min은 두 숫자 중 작은 것을 고릅니다. 전체가 12초 남았다면 다음 파일은 12초까지만 기다립니다. 남은 시간이 0 이하라면 worker를 새로 시작하지 않고 미처리 결과를 U로 남깁니다.

stdout: 최종 답안 통로

JSON 배열 하나만 냅니다. 각 파일 결과에는 아래 네 필드가 있습니다.

file원래 .sol 파일 이름
verdictMALICIOUS / BENIGN / UNCERTAIN
reasons판정 이유 문자열 목록
evidence원본 함수·줄 위치 근거

stderr: 검사실의 작업 메모

진행 상황, 컴파일 오류, 규칙의 지원 한계 같은 진단이 나옵니다. JSON과 통로를 분리해야 다른 프로그램이 답안을 읽을 수 있습니다.

근거 줄은 원본의 1행부터 셉니다. MALICIOUS에는 실제 근거를 담고, 모르는 위치는 지어내지 않습니다. confidence나 내부 보고용 메타데이터를 공개 필드로 추가하지 않습니다.

문제가 생기면 어떻게 끝내나요?
  • 한 파일 컴파일 실패: worker가 해당 파일을 U로 기록합니다.
  • 한 파일 시간 초과: CLI가 worker와 자식 프로세스 그룹을 종료하고 해당 파일을 U로 기록합니다.
  • 전체 시간 소진: 아직 시작하지 못한 파일은 미리 준비한 U 결과로 남습니다.
  • 입력 폴더가 없거나 .sol이 없음: 가짜 파일 결과를 만들지 않고 stderr와 비정상 종료로 입력 오류를 알립니다.
Docker는 이 흐름의 어디에 있나요?

Docker는 위 분석기를 실행하는 데 필요한 도구를 담은 상자입니다. 이미지에는 Python, 고정 의존성, solc와 현재 소스가 들어갑니다. Linux 환경에서 일반 사용자 권한으로 실행하고, 기본 입력 경로는 /input입니다.

빌드는 상자를 만드는 일, 실행은 그 상자로 검사하는 일입니다. 최초 의존성 설치에는 네트워크가 필요할 수 있지만 완성한 이미지의 분석 실행은 오프라인으로 동작합니다. 로컬 소스를 고쳐도 이미 만들어 둔 이미지 안의 코드는 자동으로 바뀌지 않습니다. 현재 코드를 반영하려면 재빌드해야 합니다.

실제 실행·제출 명령은 README, DOCKER.md, SUBMISSION.md를 확인하세요. 철회 전 stage1/flow 실험 이미지는 현행 코드와 구분해야 합니다.

문법쉬운 뜻이 저장소 예시

Python의 들여쓰기는 “이 작업 안에 속한다”는 뜻입니다. class와 @dataclass는 여러 정보를 묶는 자료형을 만들 때 사용합니다. 여기서는 Path나 Claim 같은 메모장의 틀로 생각하면 됩니다.

읽은 흐름 확인하기

① 일곱 규칙 중 여섯 규칙이 정상이라면 무조건 정상인가요?

아닙니다. 현재는 일곱 규칙이 등록되어 있으며 다수결을 하지 않습니다. 위험 근거가 있으면 M이 우선이고, 미해결 계약이 남으면 B로 확정하지 않습니다.

② 변수 balance의 이름을 candy로 바꾸면 의미도 바뀌나요?

이름만 바꾸고 관계가 같다면 의미는 같습니다. 분석기는 선언과 쓰기·계산·권한 관계를 읽습니다. 표시되는 변수 이름과 원본 줄 위치는 바뀔 수 있습니다.

③ 전체 시간이 8초 남았을 때 다음 파일에 60초를 주나요?

8초까지만 기다립니다. 파일 제한과 남은 전체 시간 중 작은 값을 적용합니다. 아직 처리하지 못한 파일도 결과 목록에는 U로 남습니다.

④ 이유 문장을 예쁘게 정리하면 UNCERTAIN이 줄어드나요?

설명 정리만으로는 지원 범위가 넓어지지 않습니다. reporting은 근거를 읽기 쉽게 만드는 역할입니다. 미지원 구조를 확정하려면 경로 해석과 판정 규칙에서 실제로 그 구조를 검증해야 합니다.

낯선 말은 여기서 찾아보세요

비유를 읽고, 옆의 실제 뜻을 연결하세요.

스마트 계약 / Solidity
돈이나 토큰을 다루는 규칙을 적은 프로그램 / 그 규칙을 쓰는 언어. .sol이 소스 파일입니다.
생성자 / constructor
자판기를 처음 설치하는 작업. 관리자와 초기 잔액 등을 설정합니다. 반복 호출하는 버튼과 구분합니다.
함수 / function
이름 붙은 작업 버튼. 전송·발행·출금 같은 동작의 입구입니다.
modifier
버튼에 붙이는 공통 절차. onlyOwner라는 이름보다 실제 조건과 본문이 들어가는 _ 위치가 중요합니다.
msg.sender / msg.value
이번 호출을 한 주소 / 이번 호출에 실려 온 ETH 수량입니다.
mapping / 저장소
주소별 잔액 같은 이름표 달린 장부 / 호출이 끝나도 유지되는 계약의 상태입니다.
require / revert
조건이 맞아야 계속 가기 / 실패로 실행을 취소하기. 실패하면 그 실행의 상태 변경도 되돌아갑니다.
AST / CFG / SlithIR
문법 구조 나무 / 실행 길 지도 / 계산과 변경을 분석하기 쉬운 작은 명령으로 표현한 것. Slither가 제공하는 구조입니다.
기호 표현
정확한 숫자를 몰라도 “이전 잔액 − 이번 수량”처럼 값의 관계를 저장하는 방식입니다.
guard / write / call
성공 조건 / 저장소에 기록한 변경 / 다른 코드를 호출하는 동작입니다.
승인 / allowance
다른 사람이 내 토큰을 얼마까지 옮겨도 되는지 적은 허락입니다. 사용량과 실제 이동을 연결해서 봅니다.
delegatecall
다른 주소의 코드를 내 계약의 저장소 문맥에서 실행합니다. 어떤 코드를 누가 골라 실행하는지가 중요합니다.
재진입 / reentrancy
돈을 받는 쪽의 코드가, 첫 작업이 끝나기 전에 다시 금고에 들어오는 상황입니다. 장부·잠금·지급 순서를 함께 봅니다.
