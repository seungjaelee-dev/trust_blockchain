TRUST404 분석기 전체 흐름 설명서

이 HTML은 “내가 만든 도구가 어디서 시작해서 어떤 파일을 거쳐 JSON 결과를 내는지”를 한 번에 보려고 만든 지도입니다. 10살 아이에게 설명하듯이 시작하지만, 심사위원 질문에는 바로 답할 수 있도록 핵심 근거까지 넣었습니다.

입력: .sol 폴더 출력: JSON 배열 판정: BENIGN / MALICIOUS / UNCERTAIN 오프라인: 외부 API 없음

제일 짧은 설명

이 프로그램은 Solidity 코드를 “글자”로 찍어 맞히지 않고, Slither/solc로 코드의 뼈대를 읽습니다. 그다음 “누가 호출했는지, 어떤 검사를 통과했는지, 어떤 돈 장부가 바뀌는지”를 따라가서 위험하면 막고, 확신이 부족하면 정상이라고 우기지 않고 UNCERTAIN으로 둡니다.

1. 이 문제는 무엇을 풀까?

사용자는 지갑에서 계약 서명 창을 볼 때 “이 계약이 내 돈을 빼갈 수 있는지” 잘 모릅니다. 이 프로젝트는 .sol 소스코드를 넣으면 실행 전에 위험한 길이 있는지 알려주는 도구입니다.

쉬운 비유로 말하면, 스마트 컨트랙트는 자동판매기입니다. 겉으로는 “토큰 보내기” 버튼처럼 보여도, 안쪽에 관리자만 몰래 새 쿠폰을 찍는 버튼이나 사용자 예치금을 전부 가져가는 버튼이 숨어 있을 수 있습니다.

2. 정답 세 가지

BENIGN 지원하는 범위 안에서 위험한 돈 이동이나 몰래 발행 경로가 없다고 설명할 수 있음.

MALICIOUS 다른 사람 자산 이동, 무제한 발행, 사용자 예치금 회수처럼 차단할 만한 경로가 있음.

UNCERTAIN 루프, import, assembly, 복잡한 외부 호출처럼 아직 안전하게 판단하지 못함.

3. 이 도구의 핵심 철학

글자 맞히기 금지

파일명, 주석의 LABEL, 변수 이름만 보고 판단하지 않습니다. 변수 이름이 owner라서 소유자라고 믿는 식으로 만들지 않았습니다.

흐름 보기

“누가 호출했나 → 어떤 require를 통과했나 → 어떤 상태값을 바꿨나 → 사용자가 손해 보나”를 봅니다.

모르면 보류

지원하지 않는 구조를 만나면 BENIGN으로 덮지 않고, 이유를 달아 UNCERTAIN으로 둡니다.

실행 흐름: 터미널 명령 하나가 JSON으로 바뀌는 과정

아래 칸을 눌러 보세요. 실제 프로그램의 호출 순서입니다.

실제 호출 지도

scripts/analyze.py
→
사용자가 실행하는 문입니다. 프로젝트의 src를 Python 경로에 넣고 track1.cli.main()을 부릅니다.
src/track1/cli.py
→
입력 폴더 바로 아래의 .sol 파일을 모으고, 파일마다 별도 worker 프로세스를 띄웁니다. 시간 초과면 해당 파일만 UNCERTAIN입니다.
src/track1/worker.py
→
한 파일을 Slither로 읽습니다. Slither는 solc를 이용해 AST, CFG, SlithIR 같은 코드 구조를 만듭니다.
src/track1/verdict.py
→
여러 규칙을 같은 계약에 적용합니다. 위험 규칙이 하나라도 확실하면 MALICIOUS, 미지원 핵심 경로가 있으면 UNCERTAIN, 모두 설명되면 BENIGN입니다.
src/track1/rules/*.py
→
실제 위험을 찾습니다. 토큰 발행, 승인 전송, 정지 제한, 금고 예치금, delegatecall, 재진입 같은 흐름을 봅니다.
stdout JSON
✓
심사용 출력입니다. 진행 로그는 stderr로 보내서 stdout에는 JSON 배열 하나만 남깁니다.

Python 파일끼리 어떻게 호출하나?

이 프로젝트는 “한 파일이 모든 일을 다 하는 구조”가 아닙니다. 가장 바깥의 scripts/analyze.py는 문 역할만 하고, 실제 일은 src/track1 안쪽으로 계속 넘깁니다. Python에서는 다른 파일의 함수를 import해서 부를 수 있고, 이 프로젝트는 그 방식을 씁니다.

1. 사용자가 부르는 문

# scripts/analyze.py
sys.path.insert(0, ".../src")
from track1.cli import main

if __name__ == "__main__":
    raise SystemExit(main())

뜻: src 폴더를 Python이 찾을 수 있게 하고, track1/cli.py 안의 main()을 실행합니다.

2. 파일마다 worker 실행

# src/track1/cli.py
process = subprocess.Popen([
    sys.executable,
    "worker.py",
    source,
    solc,
    output
])

뜻: .sol 하나마다 새 Python 프로세스를 띄웁니다. 한 파일이 터져도 전체 프로그램이 같이 죽지 않게 하기 위한 구조입니다.

worker 안에서는 무슨 일이 일어나나?

Slither로 Solidity 읽기

# src/track1/worker.py
from slither.slither import Slither
from track1.verdict import analyze

analysis = Slither(str(source), solc=str(solc))
result = analyze(analysis, source)

Slither(...)가 Solidity 파일을 읽고, 함수·변수·조건·중간 표현을 담은 분석 객체를 만듭니다. 그 객체를 verdict.analyze()에 넘겨서 우리 규칙으로 판정합니다.

왜 stdout을 조심하나?

# src/track1/worker.py
os.dup2(2, 1)
output.write_text(json.dumps(result))

채점 stdout에는 JSON 배열 하나만 나와야 합니다. 그래서 worker의 일반 출력은 stderr로 돌리고, 결과는 임시 파일에 써서 부모 cli.py가 읽게 합니다.

전체 로직을 코드 흐름으로 따라가기

아래 순서가 이 프로그램의 뼈대입니다. 문법을 아직 다 몰라도 “데이터가 어디서 어디로 넘어가는지”만 잡으면 코드를 읽을 수 있습니다. 입력 폴더가 들어오고, .sol 파일들이 리스트가 되고, for문으로 하나씩 분석되고, 각 결과가 다시 리스트에 담긴 뒤 JSON으로 출력됩니다.

1
사용자가 폴더를 인자로 준다 
python scripts/analyze.py reference/public

여기서 reference/public이 입력 폴더입니다. Python 코드 안에서는 이 값이 args.input_dir가 됩니다.

2
입력 폴더 바로 아래의 .sol만 고른다 
files = sorted(
    p.absolute()
    for p in args.input_dir.iterdir()
    if p.is_file() and p.suffix == ".sol"
)

iterdir()는 폴더 안 파일들을 하나씩 봅니다. p.suffix == ".sol" 조건 때문에 Solidity 파일만 남습니다. 하위 폴더까지 깊게 들어가지는 않습니다.

3
결과 리스트를 먼저 UNCERTAIN으로 채운다 
results = [
    uncertain(p, "아직 분석하지 못했습니다.")
    for p in files
]

이건 안전장치입니다. 중간에 전체 시간이 부족해져도, 최소한 모든 파일에 대한 기본 결과가 있습니다. 나중에 분석에 성공한 파일만 해당 위치가 진짜 결과로 바뀝니다.

4
for문으로 .sol 파일을 하나씩 분석한다 
for index, source in enumerate(files):
    results[index] = run_file(
        source,
        solc,
        min(args.file_timeout, remaining)
    )

source는 지금 분석할 Solidity 파일 하나입니다. run_file()은 이 파일 하나를 worker에게 맡깁니다. results[index]에 다시 넣기 때문에 입력 파일 순서와 출력 결과 순서가 맞습니다.

5
run_file이 worker.py를 새 Python으로 실행한다 
process = subprocess.Popen([
    sys.executable,
    str(worker),
    str(source),
    str(solc),
    str(output),
])

이건 함수 호출이 아니라 “새 Python 프로그램 실행”입니다. worker에게 네 가지를 줍니다. 분석할 source, 사용할 solc, 결과를 쓸 output 파일입니다. worker가 죽거나 오래 걸려도 부모 CLI가 통제할 수 있습니다.

6
worker.py가 Slither에게 Solidity를 읽힌다 
analysis = Slither(str(source), solc=str(solc))
return {
    "file": source.name,
    **analyze(analysis, source)
}

Slither(...)가 Solidity 파일의 구조를 만듭니다. 그 구조에는 함수, 변수, 조건, 상태 변경, 내부 호출 정보가 들어 있습니다. 그다음 track1.verdict.analyze를 import해서 우리 판정 로직에 넘깁니다.

7
verdict.py가 rules 검사관들을 전부 호출한다 
for contract in analysis.contracts:
    for label, rule in RULES:
        try:
            matched.append(rule(contract))
        except Unsupported as error:
            missing.append(f"{label}: {error}")

RULES에는 supply.analyze_contract, expanded_tokens.analyze_contract, expanded_vaults.analyze_contract 같은 함수들이 들어 있습니다. 즉 verdict.py가 각 컨트랙트를 들고 rules 폴더의 검사 함수들을 하나씩 찾아갑니다.

8
최종 결과를 JSON 배열 하나로 출력한다 
# worker.py
output.write_text(json.dumps(result))

# cli.py
result = json.loads(output.read_text())
results[index] = result
print(json.dumps(results, ensure_ascii=False, indent=2))

worker는 파일 하나의 결과를 임시 result.json에 씁니다. 부모 cli.py는 그 파일을 읽어서 results 리스트에 넣습니다. 모든 파일이 끝나면 리스트 전체를 stdout에 JSON 배열 하나로 출력합니다.

폴더와 파일 관계

왼쪽 목록에서 파일을 누르면 오른쪽에 역할, 들어오는 값, 나가는 값이 보입니다.

실행 코드 판정 규칙 테스트 원본 자료 문서

폴더를 한 문장으로 외우기

폴더역할심사위원에게 설명할 말
scripts/사람이 실행하는 입구와 개발 보조 도구채점자는 scripts/analyze.py를 실행하면 됩니다.
src/track1/실제 분석 엔진CLI, worker, 판정 집계, 규칙이 여기에 있습니다.
src/track1/rules/위험을 찾는 규칙 모음Slither가 만든 구조 위에서 권한, 돈 장부, 공급량 흐름을 판정합니다.
tests/회귀 테스트와 개발 문제공개 표본만 맞춘 것이 아니라 변주 문제 40개와 이름 변경 변형도 돌렸습니다.
reference/대회 원문, schema, 공개 표본 보존판정 규칙을 만들 때 원문 계약과 출력 schema를 기준으로 삼았습니다.
docs/계획, 진행, 실험 기록, 설명서무엇을 했고 무엇을 아직 못 했는지 숨기지 않고 기록했습니다.
results/로컬 실행 결과와 로그Git에는 넣지 않는 실행 산출물입니다. 사용자가 2CPU/4GB에서 돌린 결과도 여기에 있습니다.

판정 규칙을 아주 쉽게 이해하기

분석기는 먼저 “성공할 수 있는 길”만 봅니다. 예를 들어 require(x <= cap)이 실패하면 거래 전체가 취소되므로, 실패한 길은 실제 돈 이동 경로가 아닙니다. 반대로 성공 가능한 길에서 돈이나 공급량이 이상하게 바뀌면 위험합니다.

verdict.py가 rules를 호출하는 구조

네가 말한 것처럼 실제 판정 기준은 src/track1/rules/ 안에 있고, src/track1/verdict.py가 그 규칙들을 차례대로 호출합니다. 쉽게 말하면 verdict.py는 “심사위원장”, rules 파일들은 “각 분야 검사관”입니다. 

# src/track1/verdict.py 의 핵심 구조
RULES = (
    ("공급량 상한", supply.analyze_contract),
    ("고정 공급량", fixed_supply.analyze_contract),
    ("비대칭 전송", transfer_restrictions.analyze_contract),
    ("임의 코드 실행", delegatecall.analyze_contract),
    ("확장 토큰 경로", expanded_tokens.analyze_contract),
    ("확장 금고 경로", expanded_vaults.analyze_contract),
)

for label, rule in RULES:
    try:
        matched.append(rule(contract))
    except Unsupported as error:
        missing.append(f"{label}: {error}")

각 rule 함수는 계약 하나를 받아서 세 가지 중 하나를 합니다. 확실히 설명할 수 있으면 {"verdict": "...", "reasons": [...], "evidence": [...]}를 돌려줍니다. 이 규칙이 다루지 못하는 모양이면 Unsupported를 던지고, 그 이유는 missing에 쌓입니다.

위험 이유가 여러 개면 JSON에 어떻게 나오나?

결론부터 말하면, 확실한 위험 판정이 여러 개 나오면 이유도 여러 개 들어갑니다. 첫 번째 이유만 버리고 끝내는 구조가 아닙니다.

집계 코드의 핵심

# src/track1/verdict.py
malicious = [
    f for f in findings
    if f["verdict"] == "MALICIOUS"
]

if malicious:
    return {
        "verdict": "MALICIOUS",
        "reasons": [
            r for f in malicious
            for r in f["reasons"]
        ] + limitations,
        "evidence": [
            e for f in malicious
            for e in f["evidence"]
        ],
    }

예시로 이해하기

어떤 이상한 .sol이 “상한 없는 발행”과 “사용자 예치금 전체 회수”를 둘 다 갖고 있다고 합시다. 토큰 규칙과 금고 규칙이 둘 다 MALICIOUS를 돌려주면, 최종 JSON은 verdict: "MALICIOUS" 하나이고 reasons 배열 안에 두 이유가 함께 들어갑니다. 

[
  {
    "file": "weird.sol",
    "verdict": "MALICIOUS",
    "reasons": [
      "상한 없는 발행 경로...",
      "사용자 예치금 전체 회수 경로..."
    ],
    "evidence": [
      {"function": "mint(address,uint256)", "line": 27},
      {"function": "sweep()", "line": 41}
    ]
  }
]

단, 한 규칙이 이미 위험을 충분히 찾았더라도 다른 규칙이 미지원 구조를 만날 수 있습니다. 그 경우 최종 판정은 위험 증거가 우선이라 MALICIOUS이고, 미지원 설명은 reasons 뒤쪽에 붙을 수 있습니다. 반대로 위험 증거가 없고 미지원만 있으면 UNCERTAIN입니다.

정상 토큰

내 잔액에서 빠진 만큼 상대방 잔액이 늘고, 대리 전송은 승인 한도를 확인하고 사용한 만큼 차감합니다.

예: P1, allowance_safe, cap_amount_safe

위험 토큰

관리자가 상한 없이 발행하거나, 상한 검사를 우회하거나, 남의 잔액을 허락 없이 옮길 수 있습니다.

예: P2, allowance_risk, cap_branch_risk

보류

루프, assembly, import, 복잡한 외부 호출처럼 현재 작은 해석기가 안전하게 따라가지 못하는 구조입니다.

정상이라고 주장하지 않는 것이 포인트입니다.

핵심 규칙 6개

규칙보는 것위험 예시정상 예시
공급량 상한 실제로 늘어나는 공급량이 고정 상한 이하인지 한 번 발행량만 제한, 다른 분기에서 검사 생략, 상한값 자체 변경 모든 발행 경로가 newTotal <= cap을 통과
전송 권한 누구 잔액을 빼는지, 호출자가 그 권한이 있는지 아무나 from의 잔액을 빼서 다른 주소로 이동 자기 잔액 전송 또는 승인 한도 차감 전송
승인 재사용 승인 한도를 검사한 뒤 사용분을 줄이는지 한 번 받은 승인으로 반복 전송 가능 전송 후 allowance -= amount
전송 제한 정지/목록 제한이 모두에게 같은지 일반 사용자는 막히는데 관리자만 통과 정지 상태면 관리자도 똑같이 막힘
금고 예치금 사용자 예치 장부와 실제 ETH 송금이 맞물리는지 사용자 입금이 있는데 관리자가 전체 ETH를 회수 본인 장부에서 차감하고 본인에게만 출금
delegatecall / 재진입 외부 코드 실행이 금고 저장소와 돈을 바꿀 수 있는지, 지급 전후 순서가 안전한지 예치금이 있는데 관리자 임의 delegatecall, 지급 후 장부 0 대입 예치 경로 없음, 지급 전 차감, 실제 잠금, checked 차감

src/track1/rules 안의 파일들을 어떻게 읽으면 되나?

  • paths.py: 길을 먼저 만든다 함수 안의 if, require, 내부 함수 호출을 따라가며 “이 성공 경로에서는 어떤 조건을 통과했고 어떤 상태값을 썼는지”를 모읍니다.
  • expanded_tokens.py: 토큰 장부를 본다 공급량, 잔액, 승인 한도, 전송 제한을 봅니다. 상한 없는 발행, 승인 없는 남의 잔액 이동, 승인 재사용 같은 문제를 여기서 잡습니다.
  • expanded_vaults.py: ETH 금고를 본다 deposit, withdraw, 전체 회수, delegatecall, 제한된 재진입 구조를 봅니다. 사용자 예치금이라는 자산 경로가 있는지가 중요합니다.
  • supply.py, fixed_supply.py, transfer_restrictions.py, delegatecall.py: 초기 공개 표본에서 출발한 규칙 처음 공개 5개를 정확히 설명하기 위해 만든 기본 규칙입니다. 확장 규칙과 함께 verdict.py에서 모두 호출됩니다.
  • linear.py, checked.py, common.py: 도우미 실제 위험명을 붙이는 파일이라기보다, 경로 읽기·산술 검사·공통 로직을 도와주는 파일입니다.

rules 파일 전체 해설: 누가 어떤 오류를 잡나?

rules/ 안의 파일이 많아 보이는 이유는 “위험을 직접 판정하는 규칙”과 “그 규칙들이 코드를 읽도록 도와주는 도구”가 함께 들어 있기 때문입니다. Slither가 제공하는 것은 Solidity 구조이고, 아래 파일들은 그 구조를 대회 기준에 맞게 해석하는 자체 판정 계층입니다.

파일 역할 잡으려는 문제 핵심 코드/함수 어떻게 이해하면 되나
expanded_tokens.py 확장 토큰 판정 규칙 상한 우회 발행, 엉뚱한 수량 검사, 가변 상한, 승인 없는 전송, 승인 재사용, 관리자만 우회하는 정지 제한 analyze_contract(), transfer_shape(), cap_bounds(), capped() 토큰 장부 검사관입니다. “공급량과 잔액이 어떻게 늘고 줄었나”, “그 전에 올바른 검사를 했나”를 봅니다.
expanded_vaults.py 확장 ETH 금고 판정 규칙 사용자 예치금 전체 회수, 예치금과 임의 delegatecall 연결, 제한된 재진입 위험 analyze_contract() 금고 장부 검사관입니다. “사용자가 입금했나”, “출금은 본인에게 가나”, “관리자가 전체 금고를 가져갈 수 있나”를 봅니다.
supply.py 초기 공급량/발행 규칙 소유자의 상한 없는 발행, 공급량과 잔액을 같이 늘리는 직접 mint 경로 mint_shape(), check_initialization(), analyze_contract() P2/P4 같은 공개 표본에서 출발한 규칙입니다. 발행이 실제로 전송 가능한 잔액까지 늘리는지 연결합니다.
fixed_supply.py 고정 공급량 정상 경계 규칙 초기 발행 후 공급량이 변하지 않고, 전송/승인/대리 전송만 있는 정상 ERC20 비슷한 구조 allowance_type(), approve_shape(), delegated_shape(), analyze_contract() P1 같은 정상 토큰을 설명하기 위한 규칙입니다. 대리 전송에서 승인 한도 차감이 있는지 봅니다.
transfer_restrictions.py 비대칭 전송 제한 규칙 소유자는 전송 가능하지만 일반 사용자는 목록/상태 때문에 전송이 막히는 구조 analyze_contract() P3 같은 honeypot 구조를 봅니다. “소유자 초기 허용 + 소유자 목록 관리 + 발신자 제한”이 연결되는지 확인합니다.
delegatecall.py 초기 delegatecall 위험 규칙 사용자 예치 경로와 소유자 제어 delegatecall이 결합된 구조 analyze_contract() P5에서 출발한 규칙입니다. 일반 proxy 전체 판정기가 아니라, 대회 샘플형 위험 연결을 봅니다.
paths.py 확장 규칙용 경로 해석기 직접 위험을 잡기보다, 분기/require/내부 호출을 따라가며 성공 경로를 만들어 줌 trace_paths(), contract_paths(), Path 지도 제작자입니다. “이 함수가 성공하려면 어떤 조건을 지나고, 어떤 storage를 쓰는가”를 기록합니다.
linear.py 초기 규칙용 단순 IR 해석기 분기 많은 코드를 일반적으로 풀기보다, 직선 흐름의 입력값·검사식·상태 쓰기를 연결 Trace, trace_function(), symbol(), Unsupported 초기 버전의 작은 지도 제작자입니다. 미지원이면 억지로 정상 처리하지 않고 Unsupported로 멈춥니다.
checked.py checked 산술 보조 검사 Solidity 0.8의 overflow/underflow 검사 때문에 실제로는 멈추는 경로를 위험 실행으로 오인하는 문제 validate_checked(), affine() “계산하다가 거래가 취소될 수 있는가”를 보는 안전장치입니다. 위험 경로처럼 보여도 산술 실패면 실행되지 않을 수 있습니다.
common.py 초기 규칙 공통 도구 생성자/런타임 함수 분리, 선언 범위 검사, 공통 제한 확인 read_contract(), runtime(), constructor_trace(), check_declarations() 반복되는 준비 작업을 묶어 둔 파일입니다. 직접 위험명을 붙이기보다 다른 규칙을 도와줍니다.
__init__.py 패키지 표시 파일 위험 탐지 로직 없음 모듈 설명 문자열 Python에게 이 폴더가 패키지임을 알려주는 파일입니다.

전부 내가 만든 로직인가?

경계를 정확히 나누면 이렇습니다. Solidity를 파싱하고 AST/CFG/SlithIR 같은 구조를 제공하는 부분은 Slither와 solc가 맡습니다. 그 구조를 받아서 “대회 기준으로 BENIGN/MALICIOUS/UNCERTAIN 중 무엇인가”를 정하는 규칙 파일들은 이 프로젝트의 자체 판정 로직입니다.

외부 도구가 해주는 일

Solidity 문법 읽기, 컴파일 가능한 구조 만들기, 함수/변수/CFG/SlithIR 제공.

주요 도구: solc, Slither

이 프로젝트가 만든 일

상한 없는 발행인지, 승인 없는 전송인지, 예치금 회수인지, 보류할지 판단하고 JSON 이유와 근거 줄을 만드는 일.

주요 코드: verdict.py, rules/*.py, cli.py

왜 P2는 위험이고 P4는 정상인가?

P2 HiddenMint

관리자가 mint를 반복 호출해 totalSupply와 누군가의 잔액을 늘릴 수 있습니다. 그런데 “최종 공급량이 여기까지만”이라는 고정 상한 검사가 없습니다. 그래서 기존 보유자의 지분이 희석될 수 있어 MALICIOUS입니다.

P4 CappedMint

발행은 가능하지만, 발행 뒤의 공급량이 고정 상한을 넘지 않는지 검사합니다. 즉 “쿠폰을 찍을 수는 있지만 총 쿠폰 수의 천장은 못 뚫는다”는 뜻이라 대회 경계에서는 BENIGN입니다.

심사위원 질문에 답하는 짧은 말

그대로 외우기보다, 본인 말투로 바꿔서 설명하면 됩니다.

이 도구는 단순 키워드 매칭인가요?

아닙니다. 파일명, 주석 라벨, 문자열로 판정하지 않습니다. Slither/solc가 만든 코드 구조를 읽고, 변수 선언 객체와 SlithIR 연산을 따라가며 조건, 상태 변경, 외부 호출 순서를 봅니다. 예를 들어 modifier 이름이 onlyOwner인지보다 실제 조건이 msg.sender == owner인지 봅니다.

왜 Slither를 썼나요?

Solidity 파서를 처음부터 만드는 것은 이 기간에 위험합니다. Slither는 이미 AST, 제어 흐름, 중간 표현을 제공하므로 저는 그 위에 대회 라벨에 맞춘 판정 계층을 만들었습니다. 기본 Slither detector 결과를 그대로 악성으로 바꾼 것은 아닙니다.

왜 worker 프로세스를 따로 띄우나요?

한 파일이 컴파일에서 멈추거나 너무 오래 걸려도 전체 채점이 죽으면 안 됩니다. 그래서 파일마다 worker를 따로 실행하고, 제한 시간이 지나면 그 파일만 UNCERTAIN으로 돌려보냅니다. stdout은 JSON 하나로 깨끗하게 유지하고 로그는 stderr로 보냅니다.

BENIGN은 “완전히 안전”이라는 뜻인가요?

아닙니다. 이 프로젝트의 BENIGN은 “지원 범위 안에서 모든 성공 경로를 설명했고, 대회가 악성으로 보는 위험 경로를 찾지 못했다”는 뜻입니다. 모든 스마트 컨트랙트 보안 보증이나 수학적 완전 증명은 아닙니다.

UNCERTAIN을 왜 쓰나요?

대회 점수는 정답 +1, 오답 -1, 보류 0입니다. 모르는 구조를 무리하게 정상이라고 하면 오답 위험이 커집니다. 그래서 루프, import, assembly, 복잡한 외부 호출처럼 근거가 부족한 경우는 솔직하게 보류합니다.

현재 검증 결과는 무엇인가요?

공개 표본 5개와 개발 변형 40개는 기대 판정과 일치했습니다. 이름, 주석, 공백, Unicode 주석을 바꾼 의미 보존 변형에서도 판정이 유지되는지 확인했습니다. 사용자가 2CPU/4GB WSL에서 개발 40개를 28.704초에 실행한 결과도 일치했습니다. 다만 이것은 비공개셋 성능 보장은 아닙니다.

남에게 설명하는 순서

심사위원 앞에서는 내부 코드를 처음부터 다 말하지 말고, 아래 5단계로 말하면 흐름이 잡힙니다.

1
문제 정의
사용자는 서명 전 계약이 돈을 빼가거나 토큰 공급량을 몰래 바꾸는지 알기 어렵다.
2
입출력 계약
입력은 폴더 안의 .sol 파일들, 출력은 파일별 verdict/reasons/evidence JSON이다.
3
분석 방법
Slither/solc로 코드 구조를 읽고, 성공 경로의 조건과 상태 변경을 따라간다.
4
위험 판단
상한 없는 발행, 승인 없는 전송, 사용자 예치금 회수, delegatecall, 재진입처럼 사용자 손해로 이어지는 경로를 찾는다.
5
정직한 한계
지원하지 않는 구조는 정상으로 우기지 않고 UNCERTAIN으로 둔다. 오프라인 패키징과 깨끗한 재현은 제출 전 남은 작업이다.

직접 말해보기: P2

“P2는 관리자만 부를 수 있는 발행 함수가 있고, 그 함수가 총공급량과 누군가의 잔액을 늘립니다. 그런데 반복 발행을 막는 최종 상한 검사가 없습니다. 그래서 기존 사용자의 토큰 가치가 희석될 수 있어 위험으로 봅니다.”

직접 말해보기: P5

“P5는 사용자가 ETH를 예치할 수 있고, 관리자는 임의 주소와 데이터를 골라 delegatecall을 실행할 수 있습니다. delegatecall은 선택한 코드가 이 금고의 저장소 문맥에서 실행되므로 예치 장부나 자산을 바꿀 수 있습니다.”
